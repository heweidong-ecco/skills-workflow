# Matt Pocock Skills 完整技能指南：源码级深度解析

## 导读

Matt Pocock Skills 是 TypeScript 圈资深教育家、Total TypeScript 创始人 Matt Pocock 开源的 Agent 技能集，核心理念是 **“Skills for Real Engineers”（给真正工程师用的技能）** ——做真正的工程，不是 vibe coding。他把自己每天用 Claude Code 做真实工程的实践，沉淀成了一整套按需加载、可组合的模块化 Agent Skill。

与 Superpowers 的“全流程强制覆盖”不同，Matt Pocock 的设计哲学是 **“小巧、易定制、可组合”** ——技能基于数十年的工程经验打磨而成，兼容任何模型，用户可以随意修改使其成为自己的东西。

**关键数据**：GitHub 超 **24.5 万 Star**，安装量突破 **2000 万次**，当前稳定公开的正式技能约 **18-21 个**（根据版本不同有所增减）。

**核心失败模式洞察**：Matt 建立这些技能是为了修复他在 Claude Code、Codex 等编程智能体上看到的常见失败模式——最核心的问题就是 **“智能体没做我想要的事”** ，本质是人与 Agent 之间的沟通鸿沟。

**安装方式**：
- Claude Code 官方市场（只读、自动更新）：`claude plugins install mattpocock-skills`
- 或 `npx skills@latest add mattpocock/skills`（可编辑副本，可勾选技能）

> **重要**：安装器会让你选择要装的技能，务必把 `setup-matt-pocock-skills` 选上，首次使用每个仓库运行一次。


## 一、规划与设计类（前置思考，杜绝盲目编码）

### 1. grill-me（盘问 / 需求澄清）

- **概述**：对计划或设计进行一场“穷追不舍的访谈”，走遍决策树的每一个分支，直到你和 Agent 达成**共享理解（shared understanding）** 。这是 Matt 最受欢迎的 skill 之一。
- **核心原则**：**在共享理解形成前锁住执行权限**。`grill-me` 是 grilling 家族中唯一 **model-invoked** 的技能——你很少直接输入它，通常是某个你调用的 skill 在背后运行它。
- **触发时机**：在你想做出任何变更时，**每次都要使用**。专门用于非代码场景的需求对齐。
- **工作流程**：
  1. Agent 就你要构建的东西向你提出详细问题
  2. 持续追问，直到走遍决策树的每一个分支
  3. 查事实、问决策、等确认——压进一个很窄的接口
  4. 共享理解形成后，解锁执行权限
- **关键规则**：
  - 这是 `grilling` 家族的基础原语，`grill-with-docs` 是在此基础上增加了额外功能的变体
  - 核心价值在于 **“在动手之前把问题聊透”**
- **输入与输出**：
  - 输入：一个模糊的计划、设计或想法
  - 输出：经过充分盘问后达成的共享理解 + 决策树的分支确认
- **安装**：`npx skills add mattpocock/skills --skill=grill-me`

### 2. to-prd（生成产品需求文档）

- **概述**：将当前对话上下文转化为 PRD 并发布到项目 issue tracker——**不做访谈，只做综合**（synthesis），把你们已经讨论过的内容整合成正式文档。
- **核心原则**：**Do NOT interview the user**——这个技能是 `grill-me` 的下游步骤。盘问已经完成了，现在只需要把讨论结果结构化输出。
- **触发时机**：当用户想要从当前上下文创建 PRD 时使用。典型链路：`grill-me` → `to-prd`。
- **工作流程**：
  1. 探索仓库理解代码库当前状态（如果还没做的话）
  2. 使用项目领域词汇表（domain glossary），尊重相关区域的 ADR
  3. 勾勒测试 seam——优先复用现有 seam，用尽可能高的 seam，**理想情况下整个代码库只有 1 个 seam**
  4. 与用户确认 seam 是否符合预期
  5. 按模板生成 PRD，发布到 issue tracker，打上 `ready-for-agent` 标签
- **关键规则**：
  - PRD 必须包含：**Problem Statement**（用户视角）、**Solution**（用户视角）、**User Stories**（长且编号的列表，极其详尽）、**Implementation Decisions**（模块、接口、架构决策、Schema 变更、API 契约——**不包含具体文件路径或代码片段**）、**Testing Decisions**（只测外部行为，不测实现细节）、**Out of Scope**、**Further Notes**
  - 如果原型产出的代码片段比文字更精确地编码了某个决策（状态机、reducer、schema、类型形状），可以内联到相关决策中，并简要注明来自原型——只保留决策密集的部分，**不是工作 demo**
- **输入与输出**：
  - 输入：当前对话上下文 + 代码库理解
  - 输出：PRD 文档，发布到项目 issue tracker
- **安装**：`npx skills add mattpocock/skills --skill=to-prd`

### 3. to-issues / prd-to-issues（拆分任务工单）

- **概述**：将 PRD 拆分成可独立领取的 GitHub issues，使用**垂直切片（vertical slices）** 方式组织。
- **核心原则**：每个 issue 是一个**独立的垂直切片**——覆盖一个完整的行为路径，而不是孤立的函数层面工作。
- **触发时机**：PRD 生成后，需要将大块需求拆解为可逐步交付的工作单元时。
- **工作流程**：
  1. 读取 PRD 和相关上下文
  2. 识别独立可交付的垂直切片
  3. 为每个切片创建独立的 issue
  4. 如果使用本地文件作为 issue tracker，文件路径为 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，按依赖顺序从 01 编号
- **关键规则**：
  - 按 dependency order（blockers 优先）编号
  - 每个 issue 可被独立领取和处理
- **输入与输出**：
  - 输入：PRD 或需求描述
  - 输出：一组按依赖排序的独立 issue
- **安装**：`npx skills add mattpocock/skills --skill=to-issues`

### 4. design-an-interface（接口设计）

- **概述**：使用**并行子代理**为模块生成多个截然不同的接口设计方案。
- **核心原则**：不满足于一个方案——通过并行探索多个方向，找到最优接口设计。
- **触发时机**：需要设计模块接口时，尤其是当接口设计存在多种合理取舍时。
- **工作流程**：
  1. 分析模块职责和上下文
  2. 派发多个并行子代理
  3. 每个子代理生成一个截然不同的接口设计
  4. 汇总对比方案
- **关键规则**：
  - 强调“截然不同”——不是微调，而是根本性不同的设计方向
  - 利用并行子代理加速探索
- **输入与输出**：
  - 输入：模块需求描述
  - 输出：多个接口设计方案对比
- **安装**：`npx skills add mattpocock/skills --skill=design-an-interface`

### 5. request-refactor-plan（请求重构计划）

- **概述**：通过用户访谈创建详细的重构计划，使用**微小提交（tiny commits）** ，然后将计划作为 GitHub issue 提交。
- **核心原则**：重构必须拆解为**微小、可验证的提交**，每个提交都是一个安全的中间状态。
- **触发时机**：需要进行大规模重构之前。
- **工作流程**：
  1. 对用户进行访谈，理解重构目标和约束
  2. 探索代码库现状
  3. 设计微小提交序列
  4. 将计划作为 GitHub issue 提交
- **关键规则**：
  - 每个提交必须是可独立验证的
  - 重构计划必须详细到可以按步骤执行
- **输入与输出**：
  - 输入：重构需求
  - 输出：详细的重构计划（GitHub issue）
- **安装**：`npx skills add mattpocock/skills --skill=request-refactor-plan`

### 6. domain-model / codebase-design（领域建模）

- **概述**：提取 DDD 风格的**统一语言（Ubiquitous Language）** 词汇表——从当前对话中抽取领域术语和定义。
- **核心原则**：**在统一语言下，开发者之间的对话和代码的表达都来自同一个领域模型**（Eric Evans, DDD）。
- **触发时机**：在项目早期建立领域词汇时，或对话中出现了需要固化的领域术语时。
- **工作流程**：
  1. 分析当前对话中的领域术语
  2. 提取关键概念及其定义
  3. 构建统一语言词汇表
  4. 确保代码表达与领域模型一致
- **关键规则**：
  - 这是 Superpowers 中没有的、Matt Pocock 体系独有的 **vocabulary layer** 技能
  - 目的是解决 Agent“太啰嗦”的问题——有了统一语言，Agent 用词更精准
- **输入与输出**：
  - 输入：对话上下文
  - 输出：DDD 风格的统一语言词汇表
- **安装**：`npx skills add mattpocock/skills --skill=domain-model`

### 7. wayfinder（路径规划 / 大型任务地图）

- **概述**：将一大块工作（超过单个 Agent 会话能容纳的量）规划为 issue tracker 上的**共享决策工单地图**，逐个解决直到通往目的地的路径清晰。
- **核心原则**：**超过一个会话能承载的工作量，必须先绘制地图**。每个决策是一个独立工单，逐个攻克。
- **触发时机**：面对超大范围的工作（如大型重构、多周特性开发）时。
- **工作流程**：
  1. 将大块工作拆解为决策工单
  2. 在 issue tracker 上创建共享地图
  3. 逐个解决决策工单
  4. 路径清晰后进入执行阶段
- **关键规则**：
  - 决策工单是 **investigation tickets**——探索性的，不是实现性的
  - 这是 `decision-mapping` 的演进版本（该技能目前在 `in-progress` 目录）
- **输入与输出**：
  - 输入：一个超大范围的工作目标
  - 输出：决策工单地图 + 逐项解决记录
- **安装**：`npx skills add mattpocock/skills --skill=wayfinder`


## 二、开发与重构类（核心编码落地）

### 8. tdd（测试驱动开发）

- **概述**：使用**红-绿-重构循环**进行测试驱动开发，一次构建一个**垂直切片（vertical slice）** 。
- **核心原则**：**一次一个垂直切片**——每个测试覆盖一个完整的行为路径，而不是一个孤立的函数。
- **触发时机**：实现任何功能或修复 bug 时。
- **工作流程**：
  1. **RED**：写一个失败的测试
  2. 运行测试，确认失败
  3. **GREEN**：写最小实现代码通过测试
  4. 运行测试，确认通过
  5. **REFACTOR**：重构优化，保持测试通过
  6. 进入下一个垂直切片
- **关键规则**：
  - 在 Matt Pocock 的架构中，**TDD 是“红-绿引擎”** （red-green engine），被编织进主流程中，由 `implement` 技能驱动
  - 垂直切片是核心——不是水平切（先写所有测试，再写所有实现），而是垂直切（一个行为一个行为地完整实现）
- **输入与输出**：
  - 输入：功能需求或 bug 报告
  - 输出：经过 TDD 循环验证的生产代码 + 测试套件
- **安装**：`npx skills add mattpocock/skills --skill=tdd`

### 9. triage-issue（问题分诊）

- **概述**：通过探索代码库来调查报告的 bug，**定位根因**，然后创建一个带有**基于 TDD 的修复计划**的 GitHub issue。
- **核心原则**：**不要急着猜根因**——先探索、再定位、后计划。这与 Matt 的失败模式洞察一致：Agent 面对 bug 时倾向于立即猜测修复方案。
- **触发时机**：用户报告 bug、想要提交 issue、提到“triage”，或想要调查和计划修复一个问题时。
- **工作流程**：
  1. 探索代码库
  2. 定位根因（不是猜测，而是通过代码探索验证）
  3. 创建 GitHub issue
  4. issue 中包含基于 TDD 的修复计划
- **关键规则**：
  - issue 创建时使用 **triage role 状态机标签**（如 `needs-triage`、`ready-for-afk`），每个 role 映射到 issue tracker 中的真实标签字符串
  - `triage-issue` 是独立的 on-ramp 技能——专门为“Something‘s broken”场景设计的入口
- **输入与输出**：
  - 输入：bug 报告或问题描述
  - 输出：包含根因分析和 TDD 修复计划的 GitHub issue
- **安装**：`npx skills add mattpocock/skills --skill=triage-issue`

### 10. diagnosing-bugs（缺陷诊断）

- **概述**：针对**棘手缺陷和性能回退**的诊断循环。当用户说“diagnose”/“debug this”，或报告某些东西 broken/throwing/failing/slow 时使用。
- **核心原则**：**先建立反馈循环，再谈假设**。没有能复现的命令，不许谈假设。
- **触发时机**：面对复杂 bug 或性能退化，简单的修复尝试无效时。
- **工作流程**（6 阶段强制流程）：
  1. **Phase 1: Build a feedback loop**（建立反馈循环）
  2. **Phase 2: Reproduce + minimise**（复现 + 最小化）
  3. **Phase 3: Hypothesise**（假设）
  4. **Phase 4: Instrument**（插桩/测量）
  5. **Phase 5: Fix**（修复）
  6. **Phase 6: Regression-test**（回归测试）
- **关键规则**：
  - **Redact every secret first**——该技能会展示命令、输出和捕获的工件，必须先脱敏所有密钥
  - v1.0 是 breaking change，旧 skill 名 `diagnose` 已重命名为 `diagnosing-bugs`
  - 这是 Matt 失败模式 #3“代码不工作”的专用解决方案，与 `/tdd` 并列
- **输入与输出**：
  - 输入：bug 报告、性能问题描述
  - 输出：根因分析 + 修复 + 回归测试验证
- **安装**：`npx skills add mattpocock/skills --skill=diagnosing-bugs`

### 11. improve-codebase-architecture（代码库架构改进）

- **概述**：扫描代码库，发现**架构摩擦（architectural friction）** ，提出**深化机会（deepening opportunities）** ——把浅模块变成深模块的重构，呈现为可视化 HTML 报告，然后围绕你选中的候选项继续盘问（grill）。
- **核心原则**：**目标是可测试性和 AI 可导航性（AI-navigability）** 。通过深化浅模块使代码库更具可测试性。
- **触发时机**：用户想要改进架构、寻找重构机会、整合紧密耦合的模块，或让代码库更容易被 AI 导航时。
- **工作流程**：
  1. 运行 `codebase-design` skill，获取架构词汇表（module、interface、depth、seam、adapter、leverage、locality）及其原则（如 **deletion test**）
  2. 扫描代码库中的架构摩擦
  3. 提出深化机会，呈现为可视化 HTML 报告
  4. 用户选择一个候选项
  5. 围绕该候选项继续进行 `grill` 式盘问
- **关键规则**：
  - 这是 Matt Pocock 体系中独有的**架构层技能**，Superpowers 中无对应技能
  - 核心产出是可操作的 HTML 报告，而非纯文本建议
  - 基于**共享设计词汇表**（shared design vocabulary）工作
- **输入与输出**：
  - 输入：一个代码库
  - 输出：可视化 HTML 架构改进报告 + 选定候选项的深度盘问
- **安装**：`npx skills add mattpocock/skills --skill=improve-codebase-architecture`

### 12. migrate-to-shoehorn（迁移到 shoehorn）

- **概述**：将测试文件中的 `as` 类型断言迁移到 `@total-typescript/shoehorn`。
- **核心原则**：**用类型安全的测试工具替代不安全的类型断言**。
- **触发时机**：需要批量迁移测试文件中的类型断言时。
- **工作流程**：
  1. 识别测试文件中使用 `as` 类型断言的位置
  2. 替换为 `@total-typescript/shoehorn` 提供的类型安全替代方案
- **关键规则**：
  - 这是 Matt 作为 TypeScript 教育者身份的自然延伸——专注于类型安全
  - 属于工具迁移类技能，不是流程类技能
- **输入与输出**：
  - 输入：使用 `as` 断言的测试文件
  - 输出：迁移后的类型安全测试文件
- **安装**：`npx skills add mattpocock/skills --skill=migrate-to-shoehorn`

### 13. scaffold-exercises（练习脚手架）

- **概述**：创建练习目录结构，包含 sections、problems、solutions 和 explainers。
- **核心原则**：**为学习场景生成标准化结构**。
- **触发时机**：创建教学练习或学习材料时。
- **工作流程**：
  1. 按 section 组织
  2. 为每个 section 生成 problem（问题）
  3. 生成 solution（解答）
  4. 生成 explainer（讲解）
- **关键规则**：
  - 这是 Matt 作为教育者的独特技能——Superpowers 中没有对应的教学类技能
  - 输出是标准化的练习目录结构
- **输入与输出**：
  - 输入：教学主题和内容
  - 输出：完整的练习目录结构（sections/problems/solutions/explainers）
- **安装**：`npx skills add mattpocock/skills --skill=scaffold-exercises`


## 三、工程与安全类（团队工程化、环境管控）

### 14. setup-pre-commit（Pre-commit 钩子设置）

- **概述**：设置 Husky pre-commit 钩子，配合 **lint-staged、Prettier、类型检查和测试**。
- **核心原则**：**在提交前拦截质量问题**，而不是等 CI 才发现。
- **触发时机**：新项目初始化，或现有项目需要添加 pre-commit 质量门禁时。
- **工作流程**：
  1. 安装并配置 Husky
  2. 配置 lint-staged
  3. 集成 Prettier
  4. 集成类型检查
  5. 集成测试
- **关键规则**：
  - 一次性配置，覆盖所有提交前质量检查
  - 与 `git-guardrails-claude-code` 配合使用效果最佳
- **输入与输出**：
  - 输入：一个项目
  - 输出：配置好的 Husky + lint-staged + Prettier + 类型检查 + 测试的 pre-commit 流水线
- **安装**：`npx skills add mattpocock/skills --skill=setup-pre-commit`

### 15. git-guardrails-claude-code（Git 安全护栏）

- **概述**：设置 Claude Code hooks，**在危险 git 命令执行前拦截它们**（push、reset --hard、clean 等）。
- **核心原则**：**在造成不可逆损害之前拦截**。
- **触发时机**：配置 Claude Code 环境时，作为安全基础设施一次性设置。
- **工作流程**：
  1. 配置 Claude Code hooks
  2. 定义危险命令列表（push、reset --hard、clean 等）
  3. 在执行前进行拦截
- **关键规则**：
  - 这是**安全护栏**类技能——不是流程技能，而是保护性基础设施
  - 专门针对 Claude Code 环境
- **输入与输出**：
  - 输入：Claude Code 环境
  - 输出：配置好的 Git 安全拦截规则
- **安装**：`npx skills add mattpocock/skills --skill=git-guardrails-claude-code`


## 四、写作与知识沉淀类（自我迭代、长效复用）

### 16. write-a-skill（编写新 Skill）

- **概述**：以正确的结构、渐进式披露（progressive disclosure）和捆绑资源创建新的 skills。
- **核心原则**：**Skill 是模块化的可执行知识单元**，不是普通 Prompt 片段。遵循 Anthropic 和 Claude Code 原生 Skill 规范。
- **触发时机**：需要创建新技能时。
- **工作流程**：
  1. 确定技能目的和触发条件
  2. 按规范创建目录结构（`SKILL.md` + 脚本/模板/参考资料）
  3. 编写渐进式披露的内容——发现层（名称+描述）→ 激活层（完整规则）→ 执行层（附属资源）
  4. 捆绑必要资源
- **关键规则**：
  - 遵循**三段式智能调度**：发现层（仅读名称和描述）→ 激活层（加载完整规则）→ 执行层（按需调用附属文件）
  - 与常驻全局的 `CLAUDE.md` 完全隔离，采用**按需懒加载**，避免长期占用上下文
- **输入与输出**：
  - 输入：要封装的工程经验或流程
  - 输出：符合规范的完整 Skill 目录
- **安装**：`npx skills add mattpocock/skills --skill=write-a-skill`

### 17. edit-article（编辑文章）

- **概述**：通过**重组章节、提高清晰度、收紧行文**来编辑和改进文章。
- **核心原则**：**结构先行，清晰度第二，行文第三**。
- **触发时机**：需要编辑和改进一篇文章时。
- **工作流程**：
  1. 重组章节结构
  2. 提高表达清晰度
  3. 收紧行文
- **关键规则**：
  - 三个维度依次处理：结构 → 清晰度 → 行文
- **输入与输出**：
  - 输入：一篇文章草稿
  - 输出：编辑后的文章
- **安装**：`npx skills add mattpocock/skills --skill=edit-article`

### 18. obsidian-vault（Obsidian 知识库管理）

- **概述**：在 Obsidian 仓库中搜索、创建和管理笔记，支持 **wikilinks 和 index notes**。
- **核心原则**：**让 Agent 直接操作你的个人知识库**。
- **触发时机**：需要搜索、创建或管理 Obsidian 笔记时。
- **工作流程**：
  1. 在 Obsidian vault 中搜索相关笔记
  2. 创建新笔记
  3. 使用 wikilinks 建立笔记间连接
  4. 维护 index notes
- **关键规则**：
  - 这是 Matt Pocock 体系中**个人知识管理**方向的独特技能，Superpowers 中没有对应
  - 直接操作 Obsidian 仓库，实现 AI 与 PKM 的集成
- **输入与输出**：
  - 输入：搜索查询或创建请求
  - 输出：笔记操作结果（创建/搜索/链接）
- **安装**：`npx skills add mattpocock/skills --skill=obsidian-vault`


## 五、初始化配置技能

### setup-matt-pocock-skills（仓库初始化配置）

- **概述**：**不是脚本，是一次对话**。在你使用其他工程技能之前，每个仓库运行一次。它会询问你使用哪个 issue tracker、triage 时使用哪些标签、以及希望把创建的文档保存在哪里。
- **核心原则**：**先配置，后使用**。这是所有其他工程技能的前置条件。
- **触发时机**：在每个新仓库中首次使用 Matt Pocock 工程技能之前，**必须运行一次**。
- **工作流程**：
  1. 询问使用哪个 issue tracker（GitHub、Linear、或本地文件）
  2. 询问 triage 工单时使用哪些标签（`/triage` 会用到标签）
  3. 询问希望把创建的文档保存在哪里
- **关键规则**：
  - **每个仓库执行一次**
  - 如果没运行过，其他技能会提示你运行 `setup-matt-pocock-skills`
  - 这是 **on-ramp 技能**——所有工程技能的入口
- **输入与输出**：
  - 输入：仓库环境
  - 输出：配置好的 issue tracker、triage 标签词汇表和文档目录
- **安装**：`npx skills add mattpocock/skills --skill=setup-matt-pocock-skills`


## 六、架构分层与设计哲学

Matt Pocock Skills 的架构核心是 **“主流程 + 两个 on-ramp + vocabulary layer”**：

**主流程（Main Flow）** ：`grill-me` → `to-prd` → `to-issues` → `tdd` → 完成。这是大多数开发路径遵循的主干。

**两个 on-ramp（入口匝道）** ：
- **“Something‘s broken” on-ramp**：`diagnosing-bugs` + `triage-issue`——当出现 bug 时从这里进入
- **架构改进 on-ramp**：`improve-codebase-architecture`——当需要技术债清理时从这里进入

**Vocabulary Layer（词汇层，在下层运行）** ：
- `domain-model` / `codebase-design`：提供共享设计词汇表（module、interface、depth、seam、adapter、leverage、locality）
- `ubiquitous-language`：提供 DDD 风格的领域术语表
- 这层不直接参与流程，而是为上层技能提供**统一的语言基础**

**Standalone 技能（独立技能）** ：`write-a-skill`、`edit-article`、`obsidian-vault`、`migrate-to-shoehorn`、`scaffold-exercises`、`setup-pre-commit`、`git-guardrails-claude-code`——这些不参与主流程，按需独立使用。

**与 Superpowers 的核心区别**：

| 维度 | Matt Pocock Skills | Superpowers |
|:---|:---|:---|
| **设计哲学** | 小巧、可组合、可修改 | 全流程强制覆盖 |
| **流程控制** | 用户选择技能组合 | 框架强制 7 阶段 |
| **词汇层** | 有独立的 domain-model 层 | 无对应设计 |
| **架构层** | 有 improve-codebase-architecture | 无对应设计 |
| **教学场景** | 有 scaffold-exercises | 无对应设计 |
| **知识管理** | 有 obsidian-vault | 无对应设计 |
| **安装量** | 2000万+ | 120万+ |
| **GitHub Stars** | 24.5万+ | 27.9万+ |
