# Matt + Superpowers 双框架工作流完整实施文档

## 1. 方案概览

本方案将原本 177 行的 `CLAUDE.md` 拆分为三层：

- **CLAUDE.md（软引导，约 30 行）**：只保留总体原则、路径导航、一句话分工总结。
- **`.claude/rules/`（按需加载的规则文件）**：用 `paths` frontmatter 限定作用域，不污染主上下文。
- **`.claude/settings.json` + `.claude/hooks/`（硬约束）**：用 `PreToolUse` hook 拦截违规技能调用，用 `SessionStart` 注入分工提示，用 `permissions.deny` 阻止受保护文件编辑。

核心机制：**Hook 的 `exit 2` 无法被模型绕过，CLAUDE.md 的软引导只负责角色定位和导航。**

### 4.1 `.claude/rules/skills-routing.md`

```markdown
---

---
# 技能分工规则

## 需求澄清
- 只使用 Matt 的 `grill-me`。
- 不使用 Superpowers 的 `brainstorming`（由 hook 强制拦截）。

## TDD
- 只使用 Matt 的 `tdd`。
- 不使用 Superpowers 的 `test-driven-development`（由 hook 强制拦截）。

## 调试
- 复杂问题（多组件、跨模块、根因不明、已尝试多次修复未果）→ `diagnosing-bugs`
- 简单问题（单一文件、错误信息明确、可快速复现）→ `systematic-debugging`
- 无法判断复杂度时，默认走 `diagnosing-bugs`。

## 执行骨架
- 执行、审查、验证、收尾全部走 Superpowers：
  `using-git-worktrees` → `subagent-driven-development` / `executing-plans` → `requesting-code-review` → `receiving-code-review` → `verification-before-completion` → `finishing-a-development-branch`
- Matt 的 `tdd` 嵌入执行骨架内部。
```

```markdown
## 第 0 层：环境配置
- 安装 Matt 和 Superpowers。
- 运行 `setup-matt-pocock-skills`。
- 运行 `setup-pre-commit`。

## 第 3 层：每个 issue 的执行循环

## 第 4 层：测试检查阶段
- 提交前：`setup-pre-commit` 自动跑 lint、类型、单元测试。
- 任务完成：`tdd` + `verification-before-completion`。
- 分支完成：全量测试 + `requesting-code-review`。
- 端到端：`agent-browser` 或 `webapp-testing`。
- 失败诊断：`diagnosing-bugs`（复杂）或 `systematic-debugging`（简单）。
- 人工验收：用户最终确认。

## 第 5 层：修改与重构
- Bug 路径：`triage-issue` → `diagnosing-bugs` → 修复 → 回到执行循环。
- 重构路径：`improve-codebase-architecture` → `design-an-interface` → `request-refactor-plan` → `to-issues` → 回到执行循环。
- 严禁混用。

## 第 6 层：阶段完成
- `verification-before-completion` → `requesting-code-review` → 全量测试 + 人工验收 → `finishing-a-development-branch`。
```

## 6. `.claude/hooks/skill-guard.sh`

```bash
#!/usr/bin/env bash
# PreToolUse hook：拦截禁止的 Skill 调用
# 读取 stdin 的 JSON，解析 tool_input.skill 字段
# 如果调用了 brainstorming 或 test-driven-development，则 exit 2 阻止

set -euo pipefail

# 读取 stdin
INPUT=$(cat)

# 优先使用 jq 解析；如果没有 jq，尝试用 grep/sed 回退
if command -v jq >/dev/null 2>&1; then
  SKILL_NAME=$(echo "$INPUT" | jq -r '.tool_input.skill // empty')
else
  # 简单回退：提取 "skill":"xxx" 或 "skill": "xxx"
  SKILL_NAME=$(echo "$INPUT" | grep -o '"skill"[[:space:]]*:[[:space:]]*"[^"]*"' | sed 's/.*"skill"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/')
fi

# 禁止列表
FORBIDDEN=("brainstorming" "test-driven-development")

for skill in "${FORBIDDEN[@]}"; do
  if [[ "$SKILL_NAME" == "$skill" ]]; then
    echo "Blocked: 本项目管理规则禁止调用 $skill。需求澄清使用 grill-me，TDD 使用 tdd。" >&2
    exit 2
  fi
done

# 允许执行
exit 0
```

**使用说明**：
- 将文件保存到 `.claude/hooks/skill-guard.sh`。
- 赋予可执行权限：`chmod +x .claude/hooks/skill-guard.sh`。
- 如果系统没有 `jq`，脚本会回退到 grep/sed 解析，但建议安装 `jq` 以提高可靠性。
- 退出码 2 会阻止工具调用，并将 stderr 反馈给 Claude。

## 8. 验证方法

### 8.1 验证软约束是否生效

在 Claude Code 中发起一个需求澄清任务，观察是否自动触发 `grill-me`，而不是 `brainstorming`。如果触发错误，检查 `.claude/rules/skills-routing.md` 是否被正确加载（可以通过让 Claude 复述当前规则来确认）。

### 8.2 验证硬约束是否生效

故意让 Claude 调用 `brainstorming`，观察是否被 hook 拦截。如果未被拦截，检查：
- `.claude/settings.json` 的 `hooks.PreToolUse` 配置是否正确。
- `matcher` 是否为 `"Skill"`。
- `skill-guard.sh` 是否有可执行权限。
- 系统是否有 `jq`，或回退解析是否正常工作。

### 8.3 验证 permissions.deny

尝试让 Claude 编辑 `.scratch/xxx/prd.md`，观察是否被阻止。如果未被阻止，检查 `settings.json` 中的 `permissions.deny` 规则格式是否正确。

### 8.4 验证规则加载范围

在 `.claude/rules/` 下修改 `testing-gate.md` 的 `paths` 字段，确保只有匹配路径时才会加载。可以通过让 Claude 在非测试文件上下文中复述规则来验证是否未被加载。


## 9. 迭代与维护

- **新增禁止技能**：编辑 `skill-guard.sh` 中的 `FORBIDDEN` 数组，追加技能名。
- **新增规则文件**：在 `.claude/rules/` 下创建 `.md` 文件，用 `paths` frontmatter 限定范围。
- **调整分工**：修改 `.claude/rules/skills-routing.md`，然后重启会话或让 Claude 重新加载规则。
- **发现新的绕过模式**：先判断它属于“必须发生”还是“应该知道”。前者加 hook，后者加 rule。
- **Hook 调试**：如果 hook 在 `exit 0` 时输出 stdout，可能破坏工具调用。确保成功时静默，仅失败时向 stderr 输出。
