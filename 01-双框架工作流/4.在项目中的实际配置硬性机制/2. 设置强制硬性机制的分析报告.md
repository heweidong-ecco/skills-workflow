# CLAUDE.md 太长、约束太软：分层迁移方案

## 一、问题诊断：为什么你的直觉是对的

你实测的“70%以上会直接绕过 skills”，不是配置写得不够好，而是**机制选错了**。

Claude Code 官方文档明确区分了两类约束：

> Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude‘s behavior but are not a hard enforcement layer.

翻译过来就是：**settings 规则由客户端强制执行，不管 Claude 决定做什么；CLAUDE.md 只是塑造行为，不是硬约束层。**

官方给出了一张对照表：

| 关注点                       | 配置位置                           |
| :--------------------------- | :--------------------------------- |
| 阻止特定工具、命令或文件路径 | Managed settings: permissions.deny |
| 强制沙箱隔离                 | Managed settings: sandbox.enabled  |
| 代码风格和质量指南           | Managed CLAUDE.md                  |
| 行为指令                     | Managed CLAUDE.md                  |

核心结论：**“必须发生”的事写 Hook 和 permissions，“应该怎么做”的事写 CLAUDE.md 和 rules。** 你把所有东西都塞进了 CLAUDE.md，等于把所有“必须发生”的事都降级成了“建议”。

四大机制的约束力对比：

| 机制                         | 约束力                 | 加载时机         |
| :--------------------------- | :--------------------- | :--------------- |
| CLAUDE.md                    | 软约束（上下文引导）   | 每次会话全量加载 |
| Hooks                        | 硬约束（代码强制执行） | 事件触发时执行   |
| Rules（`.claude/rules/`）    | 软约束（按需加载）     | 路径匹配时加载   |
| Permissions（settings.json） | 硬约束（客户端强制）   | 每次工具调用     |

Hook 的硬约束原理：**一个以退出码 2 退出的钩子会阻止工具调用——完全阻止。钩子不受上下文窗口压力影响，它们从配置触发，而不是从 Claude 当前内存中的内容触发**。模型可以绕过指令，但绕不过 `exit 2`。


## 二、177 行 CLAUDE.md 的拆分方案

### 2.1 拆分原则

不是所有内容都需要硬约束。按“必须发生 / 应该知道 / 参考查询”三层拆分：

| 层级     | 内容类型                         | 迁移目标              | 约束力         |
| :------- | :------------------------------- | :-------------------- | :------------- |
| 硬约束层 | 禁止操作、强制门禁、权限边界     | settings.json + hooks | 客户端强制执行 |
| 规则层   | 分工规则、触发边界、路径相关规范 | `.claude/rules/`      | 按需加载       |
| 声明层   | 角色定位、总体原则、一句话总结   | CLAUDE.md             | 软引导         |

### 2.2 具体拆分

## 三、`.claude/rules/` 目录：按需加载的分工规则

### 3.1 为什么用 rules 而不是全塞 CLAUDE.md

Claude Code 会自动发现 `.claude/rules/` 目录中的 `.md` 文件，提供基于作用域和路径加载的持久指令，让特定领域的指导**不会污染 CLAUDE.md**。

规则层级按优先级排列：

1. 企业规则：`~/.claude/enterprise/rules/`
2. 用户规则：`~/.claude/rules/`
3. 项目规则：`.claude/rules/`

高优先级覆盖低优先级。推荐的目录结构：

```
.claude/rules/
├── INDEX.txt          # 人类导航（不自动加载）
├── skills-routing.md  # 技能分工规则
├── workflow.md        # 六层工作流
├── testing-gate.md    # 测试检查阶段
├── refactoring.md     # 重构路径
└── global/
    └── conflict.md    # 冲突处理
```

关键规则：**只有 `.md` 文件会被加载，`.txt`、`.json` 等被忽略**。用 `INDEX.txt`（不是 README.md）做人类导航。

### 3.2 paths frontmatter：路径作用域规则

用 YAML frontmatter 的 `paths` 字段，让规则只在当前任务触及匹配路径时加载。

**关键陷阱**：`paths` 使用逗号分隔的字符串，引号包裹。YAML 数组会被静默忽略：

正确写法：
```
paths: "src/**/*.js, src/**/*.ts"
```

错误写法（静默忽略）：
```
paths:
  - "src/**/*.js"
  - "src/**/*.ts"
```

### 3.3 具体拆分示例

**`.claude/rules/skills-routing.md`** —— 技能分工规则：

```
---
paths: ".claude/skills/**, .scratch/**"
---
# 技能分工规则

- 需求澄清只使用 Matt 的 grill-me，不使用 Superpowers 的 brainstorming
- TDD 只使用 Matt 的 tdd，不使用 Superpowers 的 test-driven-development
- 调试复杂问题走 diagnosing-bugs，简单问题走 systematic-debugging
- 执行、审查、验证、收尾走 Superpowers 执行骨架
```

**`.claude/rules/testing-gate.md`** —— 测试检查阶段（只在涉及测试文件时加载）：

```
---
paths: "**/*.test.ts, **/*.spec.ts, **/*.test.js"
---
# 测试检查阶段

- 提交前：setup-pre-commit 自动跑 lint、类型、单元测试
- 任务完成：tdd + verification-before-completion
- 分支完成：全量测试 + requesting-code-review
- 失败诊断：diagnosing-bugs（复杂）或 systematic-debugging（简单）
```


## 四、Hooks：把“必须发生”变成“无法绕过”

### 4.1 Hook 的核心价值

Hooks 在 Claude Code 生命周期的特定节点触发 shell 命令。**Hook 强制执行 prose 无法强制的内容：模型可以推理绕过一条指令，但它无法推理绕过 `exit 2`**。

关键限制：**成功时必须静默**——一个在 `exit 0` 时输出 stdout 的 hook 会破坏它正在守护的工具调用；成功时的静默是契约的一部分。

### 4.2 PreToolUse：技能调用的硬约束

Hook 事件配置在 `settings.json` 中：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Skill",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/skill-guard.sh"
          }
        ]
      }
    ]
  }
}
```

`skill-guard.sh` 的核心逻辑：读取 stdin 的 JSON，检查 `tool_input` 中的 skill 名称，如果调用了被禁止的 skill（如在需求阶段调用 `brainstorming`），则 `exit 2` 阻止调用。

Hook 事件表：

| 事件              | 触发时机         | 能否阻止 | 典型用途             |
| :---------------- | :--------------- | :------- | :------------------- |
| PreToolUse        | 工具执行前       | 是       | 阻止/修改命令        |
| PostToolUse       | 工具成功后       | 反馈     | 自动格式化、lint     |
| PermissionRequest | 权限对话框出现时 | 是       | 自动批准/拒绝        |
| UserPromptSubmit  | 提示提交时       | 是       | 添加上下文、验证     |
| Stop              | Claude 完成时    | 是       | 强制继续             |
| SessionStart      | 会话开始         | 否       | 加载上下文、设置环境 |

退出码语义：

| 退出码 | 效果                           |
| :----- | :----------------------------- |
| 0      | 成功——JSON 从 stdout 解析      |
| 2      | **阻止**——stderr 反馈给 Claude |
| 其他   | 非阻塞错误                     |

### 4.3 阻断的两种方式

**简单方式（exit 2）** ：
```bash
echo "Blocked: 需求阶段不允许调用 brainstorming" >&2 && exit 2
```

**JSON 方式（exit 0）** ：
```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Blocked"
  }
}
```

`permissionDecision` 可选值：`"allow"`（自动批准）、`"deny"`（阻止）、`"ask"`（显示对话框）。

### 4.4 SessionStart：注入分工规则

`SessionStart` 不能阻止，但可以注入上下文。用它在会话开始时注入一句话分工规则：

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "echo '需求走 grill-me，TDD 走 tdd，调试复杂走 diagnosing-bugs，执行走 Superpowers 骨架'"
          }
        ]
      }
    ]
  }
}
```

注意：官方文档指出注入型 hooks 需要谨慎使用——**#511 拆卸测试证明在 1035 万常驻 token 下 delta=0**。注入内容要极简。


## 五、Permissions：用 settings.json 替代 CLAUDE.md 中的禁止事项

### 5.1 deny 规则的优先级

Permissions 规则**由 Claude Code 强制执行，而不是由模型强制执行**。提示或 CLAUDE.md 中的说明会影响 Claude 尝试执行的操作，但不会改变 Claude Code 允许的操作。

deny 规则的行为取决于作用域：

- 裸工具名（如 `Bash`）会把工具从 Claude 的上下文中**完全移除**，Claude 永远看不到它
- 范围化规则（如 `Bash(rm *)`）会保留工具的可用性，但在匹配调用时**阻止**

deny 优先级最高：**deny 规则不能包含允许列表例外，即使更具体的 allow 规则也匹配同一调用，deny 仍然阻止**。

### 5.2 用 permissions 替代 CLAUDE.md 中的禁止事项

CLAUDE.md 第七节的禁止事项，可以迁移到 `settings.json`：

```json
{
  "permissions": {
    "deny": [
      "Edit(.scratch/**/prd.md)",
      "Write(.scratch/**/prd.md)"
    ]
  }
}
```

这比在 CLAUDE.md 里写“禁止 edit-article 用于 PRD”更硬——直接阻止对 PRD 文件的编辑，不管 Agent 用什么理由。

### 5.3 权限模式

在 settings.json 中设置 `defaultMode` 控制整体行为：

| 模式        | 描述                             |
| :---------- | :------------------------------- |
| default     | 标准行为，首次使用每个工具时提示 |
| acceptEdits | 自动接受工作目录中的文件编辑     |
| plan        | 计划模式                         |

│  - 总体原则：Matt 负责想清楚，Superpowers 负责做扎实    │
│  - 安装与项目结构声明                                 │
│  - 一句话分工总结                                     │

                       │

        │                             │
        ▼                             ▼
┌───────────────┐           ┌───────────────────┐
│ .claude/rules/│           │ settings.json      │
│（软约束，按需） │           │（硬约束，强制执行）  │
│               │           │                   │
│ skills-       │           │ hooks:            │
│ routing.md    │           │  - PreToolUse     │

**CLAUDE.md 只保留 30 行左右**：总体原则 + 路径导航 + 一句话分工。具体规则拆到 `.claude/rules/`，硬约束下沉到 `settings.json` 的 hooks 和 permissions。

**硬约束和软约束的分工**：
- “必须发生”的事（阻止工具调用、强制技能顺序、拦截危险命令）→ hooks + permissions（`exit 2` 不可绕过）
- “应该知道”的事（分工规则、工作流步骤、路径规范）→ `.claude/rules/`（按需加载，不占上下文）
- “角色定位”的事（总体原则、一句话总结）→ CLAUDE.md（软引导，每次加载）


## 七、实施步骤

**第一步：精简 CLAUDE.md。** 把 177 行压缩到 30 行左右，只保留总体原则、路径导航和一句话分工总结。其余内容全部移出。

**第二步：创建 `.claude/rules/` 目录。** 按第三节的拆分方案，把分工规则、工作流步骤、测试门禁、重构路径拆成独立的 `.md` 文件，用 `paths` frontmatter 限定加载范围。

**第三步：配置 `settings.json` 的 hooks。** 在项目级 `.claude/settings.json` 中配置 PreToolUse hook 拦截违规技能调用，SessionStart 注入分工规则。

**第四步：配置 `settings.json` 的 permissions。** 用 `deny` 规则阻止对受保护文件的编辑，替代 CLAUDE.md 中的部分禁止事项。

**第五步：验证。** 运行一次完整工作流，检查 hook 是否正确拦截违规调用。如果 hook 有 bug（如 `exit 0` 时输出 stdout 破坏了工具调用），先修复 hook 再继续。

**第六步：迭代。** 每发现一个新的绕过模式，先判断它属于“必须发生”还是“应该知道”。前者加 hook，后者加 rule。


## 八、为什么这样更可靠

你实测的 70% 绕过率，根本原因是 CLAUDE.md 是**上下文引导**，不是**客户端强制执行**。上下文会受压缩、窗口压力、子代理不继承等因素影响。Hook 和 permissions 从配置触发，不依赖 Claude 当前内存中的内容。

Claude Code 官方文档的定位很明确：**settings 规则由客户端强制执行，不管 Claude 决定做什么。CLAUDE.md 塑造行为，但不是硬约束层**。

把“必须发生”的事下沉到 hooks 和 permissions，把“应该知道”的事拆到 rules，CLAUDE.md 只保留角色声明和导航。177 行变 30 行，绕过率从 70% 降到接近零。
