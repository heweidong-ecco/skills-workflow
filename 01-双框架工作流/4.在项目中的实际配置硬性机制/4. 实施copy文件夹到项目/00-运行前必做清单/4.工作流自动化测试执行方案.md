# 双框架工作流自动化测试执行方案

## 一、核心思路：分层执行，能自动的自动，必须 Agent 的用日志验证

你的问题拆成两半：

1. **配置类测试**（文件在不在、JSON 合不合法、hook 拦不拦得住）→ **终端直接跑，不需要 Agent，不需要点击**
2. **技能触发测试**（Agent 会不会自动调用 grill-me 而不是 brainstorming）→ **必须在 Agent 会话里跑，因为触发是 Agent 的自主决策**

第二类不能靠脚本直接验证，但可以**用一个日志 hook 记录所有技能调用**，你只需要在 Agent 里输入固定 prompt，然后看日志文件即可——**不需要人工逐个检查技能是否触发，日志会告诉你**。

三层执行架构：

|  层   | 执行方式              | 是否需要 Agent | 覆盖           |
| :---: | :-------------------- | :------------: | :------------- |
|  L1   | 终端一键脚本          |     不需要     | T00-T04、T07   |
|  L2   | Agent 会话 + 日志验证 | 需要，但可批量 | 技能触发正确性 |
|  L3   | Agent 会话手动交互    | 需要，人工参与 | 端到端工作流   |

## 三、L2：Prompt Fixture + 日志验证（核心创新点）

### 3.1 原理

L2 的关键不是让脚本直接测试 Agent 行为，而是：

1. **加一个日志 hook**，把所有 Skill 调用追加写入日志文件
2. **准备一批固定 prompt**（fixture prompts）
3. **在 Agent 会话里逐个输入 prompt**（或批量跑）
4. **脚本自动检查日志**，判断每个 prompt 是否触发了正确的技能

**你不需要人眼检查技能触发。** 你只需要输入 prompt，脚本读日志判定通过/失败。

```bash
# 3. 检查日志

# 4. 查看详细日志

```

如果 `claude` CLI 不可用，走方式 C：

```bash

# 3. 回到终端执行
bash tests/check-prompt-log.sh
```

**你不需要人眼检查每个技能是否触发。** 日志会记录所有调用，脚本会判定。


## 四、L3：手动端到端测试

L3 覆盖 T06，验证完整工作流。**这一层必须人工参与**，因为 `grill-me` 是交互式盘问，无法完全脚本化。

### 4.1 执行方式

在 Claude Code 会话里，按 `tests/06-workflow-e2e.md` 的步骤逐项走一遍：

1. 输入"帮我加一个用户登录功能" → 确认触发 `grill-me`
2. 盘问过程中输入"提取统一语言" → 确认触发 `domain-model`
3. 输入"生成 PRD" → 确认触发 `to-prd`
4. 输入"拆成 issues" → 确认触发 `to-issues`
5. 选一个 issue 输入"执行这个 issue" → 确认走 Superpowers 执行骨架
6. 故意引入 bug → 确认走调试路径
7. 输入"改进架构" → 确认走重构路径
8. 输入"阶段完成" → 确认收尾流程

### 4.2 人工检查点

每步完成后，人工回答三个问题：

- 是否触发了预期技能？
- 是否触发了禁止技能（被 hook 拦截也算通过）？
- 是否遗漏了必要步骤？

**L3 的产出是一份测试报告**（用 `tests/report-template.md`），不是自动化脚本。因为交互式流程无法完全自动化。


## 五、完整执行顺序

配置落地后，按这个顺序跑一遍：

```bash
# 第 1 步：L1 静态测试（30 秒，纯终端）
bash tests/run-static.sh

# 第 2 步：L2 准备日志目录
mkdir -p .claude/logs
rm -f .claude/logs/skill-calls.log

# 第 3 步：L2 跑 prompt（如果 claude CLI 可用，否则走方式 C）
bash tests/run-prompts.sh

# 第 4 步：L2 检查日志（10 秒）
bash tests/check-prompt-log.sh

# 第 5 步：L3 手动端到端
# 打开 Claude Code，按 tests/06-workflow-e2e.md 逐项走
# 走完后填 tests/report-template.md

# 第 6 步：回归
bash tests/08-regression.sh
```


## 六、是否需要"在 Agent 窗口里输入要求执行"

分情况：

| 测试类型           | 是否需要 Agent 窗口 | 为什么                                             |
| :----------------- | :-----------------: | :------------------------------------------------- |
| L1 静态测试        |       不需要        | 纯 bash，终端直接跑                                |
| L2 Prompt 触发测试 |      **需要**       | 技能触发是 Agent 的自主决策，必须在 Agent 环境里跑 |
| L3 端到端          | **需要，且要人工**  | 交互式盘问、人工判断                               |

**关键认知**：L2 不需要人眼检查技能，只需要在 Agent 里跑 prompt，然后让脚本读日志判定。L3 才需要人眼判断，因为交互流程无法脚本化。


## 七、常见坑

### 坑 1：非交互模式下 hook 不触发

Claude Code 的 `-p` 非交互模式在部分版本中可能不触发 `SessionStart` hook，但 `PreToolUse` hook 通常会触发。建议先手动跑一次 `claude -p "帮我加一个登录功能"`，然后 `cat .claude/logs/skill-calls.log` 确认日志有内容。

如果日志为空，说明 hook 在非交互模式下未触发，改用方式 C（手动会话）。

### 坑 2：`CLAUDE_SESSION_ID` 环境变量不存在

日志 hook 里用了 `${CLAUDE_SESSION_ID:-unknown}`，如果环境变量不存在会记录 `unknown`。这不影响判定，只是丢失了会话区分度。如果需要区分，可以在 prompt 里加唯一标记。

### 坑 3：MARKER 被 prompt 内容干扰

`run-prompts.sh` 用 `MARKER:P1:START` 和 `MARKER:P1:END` 分隔日志。如果 prompt 内容里包含 `MARKER:` 字符串，会干扰解析。实际 prompt 不太可能包含这个，但如果有风险，换成更独特的标记。

### 坑 4：L2 误报

如果 Agent 触发技能后又触发另一个技能，日志会同时出现。`check-prompt-log.sh` 的 `check` 函数只判断"是否出现"，不判断"顺序"和"次数"。如果需要更严格的判定，扩展脚本支持。

### 坑 5：L3 无法完全自动化

`grill-me` 是交互式盘问，必须人工回应每个问题。试图完全脚本化 L3 会得不偿失。接受 L3 是半自动的，把 L1 和 L2 做扎实，L3 只跑关键路径。


## 八、最终执行摘要

- **能自动的全部自动**：L1 一键跑，L2 输入 prompt 后脚本读日志判定。
- **必须 Agent 的只在 Agent 里跑**：技能触发验证和端到端工作流。
- **不需要人眼检查技能**：日志 hook 记录所有调用，脚本判定通过/失败。
- **人工只在 L3 关键节点**：交互式盘问和端到端流程确认。

**一句话总结**：L1 终端一键跑，L2 输入固定 prompt 后看日志，L3 只跑关键路径的人工确认。
