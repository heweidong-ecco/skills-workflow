# obra/superpowers 14个核心 Skill 源码级完整文档

## 导读

Superpowers 是 Jesse Vincent（obra）开发的一套面向 AI 编程代理的技能框架与开发方法论，全部实现就是一套 `SKILL.md` 文件——用 Markdown 写成，包含 YAML frontmatter 定义触发条件、工作流程步骤和检查清单。框架没有自己的运行时，不锁定模型，不依赖私有 API。

当前版本包含 **14个核心技能**，分三类：开发流程类6个、质量保证类4个、调试与元技能类4个。

**技能触发机制**：Agent 在响应任何请求之前会检查相关技能。`using-superpowers` 的规则明确要求：即使只有1%的可能性技能适用，也必须调用技能进行检查。会话启动时，框架通过 Hook 机制注入一个引导文档（小于2000 tokens），告诉 Agent 开始任何任务前先读取相关 Skill。

**技能加载架构**（来自 `lib/skills-core.js`）：通过 `extractFrontmatter()` 读取 YAML header 识别技能名称和触发条件；`findSkillsInDir()` 递归搜索目录（最深3层）构建技能注册表；`resolveSkillPath()` 处理技能覆盖——个人技能可覆盖内置 Superpowers 技能。

**安装方式**（统一命令）：
```bash
npx skills add obra/superpowers --skill <skill-name>
# 或安装全部
npx skills add obra/superpowers
```


## 一、开发流程类（6个）

### 1. brainstorming（头脑风暴）

- **概述**：在开始任何创作性工作（创建功能、构建组件、添加功能或修改行为）之前，通过苏格拉底式对话将模糊想法转化为完整的设计和规格说明。
- **核心原则**：**未获得用户明确批准前，绝不允许 AI 动手写一行代码。** 所有项目——无论看起来多简单——都必须经过这一流程。探索用户意图、需求和设计，然后才进入实现。
- **触发时机**：任何创造性工作开始之前。具体来说，创建功能、构建组件、添加功能、修改行为时，必须使用此技能。
- **工作流程**：
  1. 将请求分类为可行性验证、已有流程的小改动或架构级工作
  2. 了解项目当前状态（检查文件、文档、最近的提交）
  3. 一次只问一个澄清问题，逐步理解需求——每次只问一个问题，不要一次抛出一堆问题
  4. 提出2-3种方案，分析权衡（性能、复杂度、可维护性），给出推荐建议
  5. 分段呈现设计，**每一段获得用户批准后才能继续**
  6. 最终产出设计文档 `docs/plans/YYYY-MM-DD-<主题>-design.md`
- **关键规则**：
  - 在呈现设计并获得用户批准之前，不得调用任何实现技能、编写任何代码、搭建任何项目脚手架
  - 设计要分段呈现，逐段获得批准
  - 方案必须包含权衡分析，不能只给一个方案
- **输入与输出**：
  - 输入：用户的功能需求描述（可以很模糊）
  - 输出：设计文档（`docs/plans/YYYY-MM-DD-<主题>-design.md`），包含问题定义、候选方案、权衡分析和推荐架构决策
- **安装**：`npx skills add obra/superpowers --skill brainstorming`


### 2. writing-plans（编写计划）

- **概述**：在获得批准的设计方案后，将设计拆解为详细、可执行的实施计划，假设执行者对我们的代码库零上下文、品味存疑。
- **核心原则**：**每个步骤是一个动作（2-5分钟）**，步骤包含精确的文件路径、完整代码（禁止TBD/TODO占位符）和验证命令。DRY、YAGNI、TDD、频繁提交。假设执行者是一个有技能的开发者，但几乎不了解我们的工具集或问题领域，也不懂好的测试设计。
- **触发时机**：有一个 spec 或需求，需要执行多步骤任务，在接触代码之前。它是 brainstorming 的终端状态——当设计批准后自动激活。
- **工作流程**：
  1. 宣告：“I‘m using the writing-plans skill to create the implementation plan.”
  2. 将设计拆解为咬合式任务，每个步骤是2-5分钟的动作
  3. 每个任务包含：**Files**（Create/Modify/Test的精确路径）、**Step 1： Write the failing test**（完整代码）、**Step 2： Run test to verify it fails**（精确命令和预期输出）、**Step 3： Write minimal implementation**（完整代码）、**Step 4： Run test to verify it passes**、**Step 5： Commit**（精确git命令）
  4. 保存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`
  5. 计划完成后提供执行选择：Subagent-Driven（当前会话）或 Parallel Session（新会话）
- **关键规则**：
  - 精确文件路径始终写明
  - 计划中包含完整代码（不是“添加验证”这样的模糊描述）
  - 精确命令和预期输出
  - 每个步骤必须可验证
  - 保存后必须提供执行选项让用户选择
- **输入与输出**：
  - 输入：已批准的设计文档
  - 输出：实施计划文件（`docs/plans/YYYY-MM-DD-<feature-name>.md`），包含咬合式任务列表、精确文件路径、完整代码和验证命令
- **安装**：`npx skills add obra/superpowers --skill writing-plans`


### 3. executing-plans（执行计划）

- **概述**：在独立会话中加载已写好的实施计划，批判性审查后逐批执行，每个检查点进行验证。
- **核心原则**：**加载计划→批判性审查→执行所有任务→报告完成。** 在每个检查点（通常每3个任务）暂停并报告进度。
- **触发时机**：有一个写好的实施计划，需要在独立会话中执行，带审查检查点。如果子代理可用，应优先使用 subagent-driven-development 而不是此技能。
- **工作流程**：
  1. 宣告：“I’m using the executing-plans skill to implement this plan.”
  2. 加载计划文件，批判性审查计划是否有问题
  3. 创建 TodoWrite，包含所有任务
  4. 按批次执行任务，每个批次（约3个任务）完成后暂停
  5. 每个检查点报告：完成情况、验证结果、任何问题
  6. 全部完成后提供分支收尾选项
- **关键规则**：
  - 每批3个任务暂停检查
  - 每个任务完成后验证
  - 如果发现问题，停下来讨论而不是继续
  - 如果子代理可用，优先使用 subagent-driven-development
- **输入与输出**：
  - 输入：实施计划文件路径
  - 输出：已执行的代码变更 + 每批完成报告 + 分支收尾建议
- **安装**：`npx skills add obra/superpowers --skill executing-plans`


### 4. subagent-driven-development（子代理驱动开发）

- **概述**：通过为每个计划任务派发一个全新的子代理来执行实施计划，任务之间进行代码审查。**核心 Skill，会话内执行实现计划的标准方式。**
- **核心原则**：**Fresh subagent per task + review between tasks = high quality, fast iteration.** 子代理**绝不继承当前会话的上下文或历史**——协调者精确构建子代理所需的内容，既保证了子代理的专注性，也保护了协调者自身的上下文空间。
- **触发时机**：在当前会话中执行实施计划，任务大多独立，希望持续进展并带有质量门禁。
- **工作流程**：
  1. 加载计划文件，创建 TodoWrite 包含所有任务
  2. 对每个任务：派发全新子代理，提供精确任务描述
  3. 子代理实现 → 写测试 → 验证 → 提交 → 报告
  4. 派发代码审查子代理，提供：BASE_SHA、HEAD_SHA、任务要求、实现摘要
  5. 审查返回：Strengths、Issues（Critical/Important/Minor）、Assessment
  6. Critical 问题立即修复，Important 问题在下一任务前修复
  7. 标记任务完成，进入下一任务
  8. 所有任务完成后派发最终代码审查（审查整个分支）
- **关键规则**：
  - **连续执行原则**：不要在每个任务之间暂停询问用户。“Should I continue？” 提示是在浪费用户时间——用户要求你执行计划，那就执行它
  - 每个任务必须有审查门禁
  - 子代理不继承协调者的上下文
  - Critical 问题必须立即修复
- **输入与输出**：
  - 输入：实施计划文件
  - 输出：每个任务完成代码 + 每个任务的审查报告 + 最终全分支审查
- **安装**：`npx skills add obra/superpowers --skill subagent-driven-development`


### 5. dispatching-parallel-agents（并行子代理调度）

- **概述**：当有多个互不依赖的任务时，派发多个子代理并行处理，大幅提升效率。
- **核心原则**：为每个独立任务分配上下文完全隔离的子智能体，并行执行开发任务；每个子智能体的执行过程互不干扰，任务完成后输出独立的交付内容与验证结果，确保并行执行过程中无上下文污染。
- **触发时机**：writing-plans 输出的任务列表中存在多个完全解耦、无依赖的独立任务时自动触发。
- **工作流程**：
  1. 识别任务列表中完全解耦、无依赖的任务
  2. 为每个独立任务派发一个子代理
  3. 每个子代理独立执行，无上下文共享
  4. 各子代理完成后汇报结果
  5. 协调者汇总并检查冲突
- **关键规则**：
  - 仅适用于完全解耦的任务
  - 有依赖关系的任务不能并行
  - 子代理之间无上下文共享
  - 需要启用多代理模式（`multi_agent = true`）
- **输入与输出**：
  - 输入：任务列表
  - 输出：各并行任务的独立交付结果
- **安装**：`npx skills add obra/superpowers --skill dispatching-parallel-agents`


### 6. using-git-worktrees（Git 工作树）

- **概述**：创建独立的 Git worktree，让开发环境和主分支物理隔离，互不影响。
- **核心原则**：Git worktrees 创建共享同一仓库的隔离工作空间，允许同时在多个分支上工作而无需切换。主分支始终保持稳定，可以放心在 worktree 中实验。
- **触发时机**：在开始需要与当前工作空间隔离的功能工作之前，或在执行实施计划之前。
- **工作流程**：
  1. 宣告：“I‘m using the using-git-worktrees skill to set up an isolated workspace.”
  2. 智能目录选择——优先使用平台原生 worktree 工具
  3. 安全验证——确保主分支状态干净
  4. 创建 worktree，无原生工具时回退到手动 `git worktree` 命令
  5. 在新 worktree 中完成项目环境搭建
- **关键规则**：
  - 优先使用平台原生 worktree 工具
  - 必须验证主分支状态干净
  - worktree 目录位置需智能选择
- **输入与输出**：
  - 输入：当前工作目录
  - 输出：独立的 Git worktree 环境
- **安装**：`npx skills add obra/superpowers --skill using-git-worktrees`


## 二、质量保证类（4个）

### 7. test-driven-development（TDD 强制执行）

- **概述**：实现任何功能或 bugfix 时，强制红-绿-重构循环。**TDD 不仅仅是写测试——它是先证明测试有效，然后再信任它。**
- **核心原则**：**Write code before the test? Delete it. Start over. NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST.** 如果你没有亲眼看到测试失败，你就不知道它是否测试了正确的东西。违反规则的文字就是违反规则的精神。
- **触发时机**：实现任何功能或 bugfix 时，在写实现代码之前。
- **工作流程**：
  1. **RED**：写一个失败的测试
  2. 运行测试，确认它失败
  3. **GREEN**：写最小实现代码通过测试
  4. 运行测试，确认通过
  5. **REFACTOR**：重构优化，保持测试通过
  6. 频繁提交
- **关键规则**：
  - 在测试之前写代码？删掉，重新开始
  - 不要保留为“参考”、不要“改编”它、不要看它——删除就是删除
  - 测试后写 = “这个代码做什么？” 测试先写 = “这个代码应该做什么？”
  - 手工测试 ≠ 系统性测试。没有记录、不能重跑、容易遗漏边界情况
  - TDD 是务实的：在提交前发现 bug、防止回归、记录行为、支持重构
- **输入与输出**：
  - 输入：功能需求或 bug 报告
  - 输出：经过 TDD 循环验证的生产代码 + 测试套件
- **安装**：`npx skills add obra/superpowers --skill test-driven-development`


### 8. requesting-code-review（发起代码审查）

- **概述**：派发代码审查子代理，在问题级联之前捕获它们。审查者获得精确构建的上下文——绝不是你的会话历史。
- **核心原则**：派发审查子代理时提供精确构建的上下文：WHAT_WAS_IMPLEMENTED、PLAN_OR_REQUIREMENTS、BASE_SHA、HEAD_SHA、DESCRIPTION。审查者返回结构化的 Strengths、Issues（Critical/Important/Minor）、Assessment。
- **触发时机**：完成任务、实现主要功能或合并之前。
- **工作流程**：
  1. 获取当前分支的 git diff
  2. 构建审查上下文：实现了什么、计划要求是什么、BASE_SHA、HEAD_SHA、任务描述
  3. 派发代码审查子代理
  4. 审查者逐文件审查
  5. 返回结构化审查报告
  6. Critical 问题阻止推进
- **关键规则**：
  - 审查者获得精确构建的上下文，绝不继承会话历史
  - Critical 问题必须阻止继续推进
  - 审查报告按严重程度分类
- **输入与输出**：
  - 输入：代码变更（git diff）+ 任务要求
  - 输出：结构化审查报告（Strengths / Issues / Assessment）
- **安装**：`npx skills add obra/superpowers --skill requesting-code-review`


### 9. receiving-code-review（接收审查反馈）

- **概述**：在实施代码审查意见之前评估其技术正确性。要求完整阅读反馈，验证其合理性，逐条处理。
- **核心原则**：**技术严谨，而非表演性同意或盲目实施。** 一个可重复的响应模式：READ → UNDERSTAND → VERIFY → EVALUATE → RESPOND → IMPLEMENT。
- **触发时机**：收到代码审查反馈时，在实施建议之前，特别是当反馈似乎不清楚或技术上有问题时。
- **工作流程**：
  1. **READ**：完整阅读所有反馈
  2. **UNDERSTAND**：理解每条反馈的意图
  3. **VERIFY**：验证反馈的合理性
  4. **EVALUATE**：评估每条反馈的技术正确性
  5. **RESPOND**：技术性地回应，不盲目认错也不抵触批评
  6. **IMPLEMENT**：在验证需求和技术上下文后才修改代码
- **关键规则**：
  - 不盲目认错，不抵触批评
  - 仅在验证需求和技术上下文后修改代码
  - 对不清楚或技术上有问题的反馈要提出质疑
- **输入与输出**：
  - 输入：代码审查反馈
  - 输出：逐条处理的反馈响应 + 修改后的代码（如确认需要修改）
- **安装**：`npx skills add obra/superpowers --skill receiving-code-review`


### 10. verification-before-completion（完成前验证）

- **概述**：在声称任何修复或功能完成之前，必须运行验证命令并确认输出。
- **核心原则**：**Evidence before claims, always.** 声称工作完成而不经验证是不诚实，而非效率。在声称工作完成、修复、通过、构建成功或可合并前，必须运行验证命令并确认输出。
- **触发时机**：声称任何修复或功能完成之前。
- **工作流程**：
  1. 识别需要验证的声明（完成/修复/通过/构建成功/可合并）
  2. 运行相应的验证命令
  3. 确认输出与预期一致
  4. 记录证据
  5. 只有在证据支持时才做出声明
- **关键规则**：
  - 没有证据不允许声明完成
  - 验证命令必须实际运行，不能靠推测
  - 输出必须确认符合预期
- **输入与输出**：
  - 输入：待声明的完成状态
  - 输出：验证证据 + 基于证据的声明
- **安装**：`npx skills add obra/superpowers --skill verification-before-completion`


## 三、调试与元技能类（4个）

### 11. systematic-debugging（系统化调试）

- **概述**：消除调试中的猜测行为。随机修复浪费时间并制造新 bug，快速补丁掩盖了底层问题。
- **核心原则**：**ALWAYS find root cause before attempting fixes. NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST.** 如果你没有完成第一阶段，你就不能提出修复方案。症状修复就是失败。违反这个流程的文字就是违反调试的精神。
- **触发时机**：遇到任何技术问题：测试失败、生产环境 bug、意外行为、性能问题、构建失败、集成问题。**尤其在时间压力下、当“快速修复”似乎很明显时、当你已经尝试了多个修复时、当前一个修复没有生效时、当你不完全理解问题时。**
- **工作流程**：
  - **Phase 1： Root Cause Investigation（根因调查）**
    - 完整阅读错误信息，不跳过错误或警告
    - 稳定复现——能否可靠触发？确切步骤是什么？
    - 检查最近的变更——Git diff、最近提交、新依赖
    - 在多组件系统中收集证据：在每个组件边界记录进入和退出的数据，运行一次收集证据，然后分析
    - 追溯数据流：坏值从哪里来？谁调用了它？向上追溯直到找到源头，在源头修复而非症状处
  - **Phase 2： Pattern Analysis（模式分析）**
    - 在同一个代码库中找到类似的工作示例
    - 与参考实现对比
    - 确定差异点
  - **Phase 3： Hypothesis and Testing（假设与测试）**
    - 形成具体假设
    - 设计最小测试验证假设
    - 证据支持假设才继续
  - **Phase 4： Implementation（实施修复）**
    - 在根因确认后进行修复
    - 回归测试通过
- **关键规则**：
  - 没有证据不得进行修复
  - 症状修复 = 失败
  - 不要跳过简单问题的系统化流程——“简单”的 bug 也有根因
  - 在组件边界收集证据，而不是猜测
- **输入与输出**：
  - 输入：技术问题（bug、测试失败、意外行为等）
  - 输出：根因分析 + 基于根因的修复 + 回归测试验证
- **安装**：`npx skills add obra/superpowers --skill systematic-debugging`


### 12. writing-skills（编写新技能）

- **概述**：创建新 Skill、编辑现有 Skill、或在部署前验证 Skill。**编写技能就是测试驱动开发应用于流程文档。**
- **核心原则**：**If you didn‘t watch an agent fail without the skill, you don’t know if the skill teaches the right thing.** 你写测试用例（带子代理的压力场景），观察它们失败（基线行为），编写技能（文档），观察测试通过（代理遵守规则），然后重构（堵住漏洞）。整个技能创建过程遵循 RED-GREEN-REFACTOR。
- **触发时机**：创建新技能、编辑现有技能、或在部署前验证技能时。
- **工作流程**：
  1. **写测试先行**：在写技能之前运行基线场景
  2. **观察它失败**：记录代理使用的确切合理化借口
  3. **写技能**：针对那些具体违规行为编写技能文档
  4. **观察它通过**：验证代理现在遵守规则
  5. **重构循环**：找到新的合理化借口 → 堵住 → 重新验证
- **关键规则**：
  - 技能是经过验证的技术、模式或工具的参考指南
  - 技能不是“关于你如何解决某个问题”的叙述
  - 只有当你确实看到代理在没有技能时失败，你才知道技能教了正确的东西
  - 创建条件：技术不直观、会跨项目引用、模式适用广泛、对他人有益
  - 不创建条件：一次性解决方案、已有良好文档的标准实践、项目特定约定
- **输入与输出**：
  - 输入：需要封装的经验、流程或技术
  - 输出：符合规范的 SKILL.md 文件
- **安装**：`npx skills add obra/superpowers --skill writing-skills`


### 13. using-superpowers（Superpowers 激活与恢复）

- **概述**：元技能，建立技能使用的基本规则，负责发现、加载和调度所有其他技能。
- **核心原则**：**即使只有1%的可能性技能适用，也必须调用技能进行检查。** 技能是强制性工作流，而非建议。当技能适用于某项任务时，Agent 必须使用它，没有例外。
- **触发时机**：任何对话开始时自动生效。
- **工作流程**：
  1. 会话启动时，框架通过 Hook 注入引导文档（小于2000 tokens）
  2. 告诉 Agent 开始任何任务前先读取相关 Skill
  3. Agent 在响应任何请求之前检查相关技能
  4. 如果1%的可能性技能适用，必须调用技能进行检查
  5. 当子代理跳过约束时，手动触发此技能可将其拉回正轨
- **关键规则**：
  - 用户指令高于 Superpowers 规则
  - 平台不一致时走 tool mapping
  - 技能是强制性的，不是建议
  - 如果你不需要超能力规则约束，说“让我们跳过超能力”即可停用
- **输入与输出**：
  - 输入：任何用户请求
  - 输出：正确的技能调用和流程执行
- **安装**：`npx skills add obra/superpowers --skill using-superpowers`


### 14. finishing-a-development-branch（开发分支收尾）

- **概述**：当实现完成、所有测试通过后，指导开发工作的完成，提供合并、PR 或清理的结构化选项。
- **核心原则**：**Verify tests → Detect environment → Present options → Execute choice → Clean up.** 提供一个可重复、安全的工作流。
- **触发时机**：实现完成、所有测试通过，需要决定如何集成工作时。
- **工作流程**：
  1. **Verify tests**：运行全量测试，确认通过
  2. **Detect environment**：检测当前环境（分支状态、worktree 状态）
  3. **Present options**：提供四选一：合并到主分支、创建PR、保留分支、丢弃分支
  4. **Execute choice**：执行用户选择
  5. **Clean up**：自动清理 worktree
- **关键规则**：
  - 必须先验证所有测试通过
  - 提供四个明确选项
  - 自动清理 worktree
  - 输出分支变更明细和代码修改统计
- **输入与输出**：
  - 输入：已完成的开发分支
  - 输出：分支合并/PR/保留/丢弃 + worktree 清理
- **安装**：`npx skills add obra/superpowers --skill finishing-a-development-branch`


## 四、核心设计理念与已知问题

### 四大核心原则

Superpowers 建立在四个核心原则之上，这些不仅仅是指导方针——它们由技能系统强制执行：

1. **Test-Driven Development**：先写测试，始终如此
2. **Systematic over Ad-hoc**：流程优于猜测
3. **Complexity Reduction**：简单是首要目标
4. **Evidence over Claims**：在声明成功之前先验证

### 7阶段强制工作流

Superpowers 把软件开发的一次完整迭代拆成7个强制阶段，框架要求不允许跳过：

1. **Brainstorming（需求澄清）** → 设计文档
2. **Writing Plans（任务拆解）** → 实施计划
3. **Using Git Worktrees（环境隔离）** → 独立 worktree
4. **Test-Driven Development（TDD实现）** → 红-绿-重构
5. **Subagent-Driven Development / Executing Plans（执行）** → 每任务审查
6. **Requesting Code Review / Verification（审查与验证）** → 审查报告 + 验证证据
7. **Finishing a Development Branch（分支收尾）** → 合并/PR/保留/丢弃

### 已知问题

- **简单任务过重**：改个文案也要走 Brainstorm 流程，可能让人感到繁琐（但可以手动跳过）
- **并行 Agent 偶尔冲突**：Git Worktree 合并时极少数情况会有冲突，需手动解决
- **Token 消耗增加**：完整工作流比直接写代码多消耗 10-20% Token
- **子代理跳过审查**：子 Agent 启动时不继承启动注入的上下文，导致有时会跳过 TDD 约束或规格/质量审查步骤直接开写。手动触发 `using-superpowers` skill 可将其拉回正轨


## 五、按角色推荐组合

- **个人开发者/独立开发者**：`brainstorming` + `writing-plans` + `subagent-driven-development` + `test-driven-development`
- **团队协作场景**：`brainstorming` + `using-git-worktrees` + `subagent-driven-development` + `requesting-code-review` + `finishing-a-development-branch`
- **大型复杂项目**：`brainstorming` + `writing-plans` + `dispatching-parallel-agents` + `subagent-driven-development` + `systematic-debugging` + `verification-before-completion`
- **轻度使用**：`brainstorming` + `using-superpowers`
