# Matt + Superpowers 双框架工作流完整指南

## 引言

当两套成熟的 Agent Skills 框架同时进入一个项目时，最大的风险不是技能不够用，而是两套框架互相争夺触发权。Matt Pocock Skills 擅长把模糊需求变成清晰规格，Superpowers 擅长把规格变成经过验证的代码。把它们放在一起，关键不在于“装哪些”，而在于“谁负责哪个阶段、怎么装、怎么触发”。

本文分八个部分：总体原则、安装策略、目录结构、触发策略、冲突处理、六层工作流详解、最终配置清单、常见错误与避坑指南。


## 一、总体设计原则

整份工作流只围绕一条主线：

**Matt 负责“想清楚”，Superpowers 负责“做扎实”。**

这条主线决定了所有后续决策。Matt 层的核心价值在需求、领域建模、架构决策、bug 分诊——这些是项目级、随仓库变化的。Superpowers 层的核心价值在执行骨架、TDD、审查、验证、收尾——这些是通用工程纪律，跨项目一致。

明确了这条主线，就能回答下面三个问题：

- 谁装在插件里，谁装在项目里？
- 谁自动触发，谁手动触发？
- 重叠技能怎么二选一？


## 二、安装策略：插件安装 vs 项目内安装

### 2.1 两种安装方式的本质区别

**插件安装**是全局生效的。一次安装，所有项目共享，自动更新，版本由市场维护。它适合不随项目变化的通用技能。它的代价是不能按项目修改，不能提交到团队 Git。

**项目内 skills 文件**是项目级生效的。只影响当前仓库，可以提交 Git，可以按项目裁剪、修改、重写。它适合随项目变化的技能。它的代价是每个项目要复制一份，版本可能漂移。

### 2.2 为什么 Matt 层必须项目内安装

Matt 的 `setup-matt-pocock-skills` 本身就设计成 **per-repo（每个仓库运行一次）**。它会问你：issue tracker 用哪个？triage 标签是什么？文档放哪里？

这说明 Matt 层天生是项目级的。插件安装会丢失这个核心设计——你没法让所有项目共享同一份 issue tracker 配置，也没法在某个项目里单独修改 triage 标签。

### 2.3 为什么 Superpowers 层必须插件安装

Superpowers 的 `using-superpowers` 是通过 hook 注入的全局行为。它需要在所有项目里保持一致——无论是个人项目还是团队项目，执行骨架、TDD 规则、审查流程都应该是同一套。

项目内安装反而会导致每个项目复制 14 个技能，维护成本高，还容易版本漂移。

### 2.4 推荐方案

- **Superpowers 层**：插件安装，全局生效。命令：`/plugin install superpowers@claude-plugins-official`
- **Matt 层**：项目内安装，提交 Git。命令：`npx skills@latest add mattpocock/skills`

装完后，首次在每个仓库运行一次 `setup-matt-pocock-skills`，配置 issue tracker、triage 标签、文档目录。


## 三、目录结构与层级隔离

### 3.1 为什么不平铺

平铺的意思是：把 Matt 的 18 个技能和 Superpowers 的 14 个技能放在同一个技能池里，让 Agent 自由选择。

平铺会直接导致三个冲突：

**冲突一：需求澄清双入口。** Matt 的 `grill-me` 和 Superpowers 的 `brainstorming` 做同一件事。Superpowers 的 `using-superpowers` 规则是“1% 可能就要调用”，它会强制 Agent 优先检查 Superpowers 的技能，Matt 的 `grill-me` 会被压住。

**冲突二：TDD 双入口。** Matt 的 `tdd` 和 Superpowers 的 `test-driven-development` 逻辑几乎一致，但触发条件不同。平铺后可能出现两个 TDD 技能都被触发，或互相认为对方该负责。

**冲突三：调试双入口。** Matt 的 `diagnosing-bugs` 是 6 阶段流程，Superpowers 的 `systematic-debugging` 是 4 阶段流程。平铺后 Agent 可能在两个流程之间反复横跳。

### 3.2 推荐结构

Claude Code 的技能加载遵循 **项目级 > 用户级 > 插件级** 的优先级。推荐结构如下：

- **项目级**：`.claude/skills/matt/` 放 Matt 的 18 个技能
- **插件级**：Superpowers 通过插件市场安装，不占项目目录
- **项目配置文件**：`CLAUDE.md` 或 `AGENTS.md` 写清楚“需求阶段用 Matt，执行阶段用 Superpowers”

不平铺的意思就是：Matt 的 `grill-me` 和 Superpowers 的 `brainstorming` 不在同一层级被同时考虑——项目配置明确告诉 Agent，需求澄清只走 `grill-me`。


## 四、触发策略：手动 vs 自动

### 4.1 关键澄清

触发方式不是安装方式决定的，是 **技能设计 + 项目配置** 共同决定的。插件安装的技能也可以手动触发，项目内的技能也可以自动触发。

### 4.2 Matt 层推荐手动触发为主

- `grill-me`：用户主动调用，或由 `to-prd` 上游触发
- `domain-model`：对话中自动提取，但结果需要用户确认
- `to-prd` / `to-issues`：用户主动调用
- `improve-codebase-architecture`：用户主动调用
- `design-an-interface` / `request-refactor-plan`：用户主动调用
- `triage-issue` / `diagnosing-bugs`：用户报告 bug 时触发

### 4.3 Superpowers 层推荐自动触发为主

- `using-superpowers`：会话启动时 hook 自动注入
- `using-git-worktrees`：进入实现阶段自动触发
- `subagent-driven-development` / `executing-plans`：有完整计划后触发
- `test-driven-development`：写实现代码前触发
- `requesting-code-review` / `receiving-code-review`：任务间触发
- `verification-before-completion`：声称完成前触发
- `finishing-a-development-branch`：所有任务完成、测试通过后触发

### 4.4 手动触发的实现方式

手动触发不靠安装方式，靠 **项目配置文件里的规则约束**。在 `CLAUDE.md` 中写：

- 需求澄清阶段只使用 Matt 的 `grill-me`，不使用 Superpowers 的 `brainstorming`
- TDD 阶段只使用 Matt 的 `tdd` 或 Superpowers 的 `test-driven-development`，二者只能选一个
- 调试阶段优先使用 Matt 的 `diagnosing-bugs`，简单问题可以用 Superpowers 的 `systematic-debugging`

这样 Agent 在触发技能时就有了明确的决策树，不会随机在两套之间摇摆。


## 五、冲突处理：重叠技能怎么办

Superpowers 的 `using-superpowers` 规则是“即使只有 1% 可能性，也必须调用技能进行检查”。这条规则在只有 Superpowers 一套时是优势，在双框架下是麻烦。

三种处理方式：

**方式一：项目配置声明优先级。** 在 `CLAUDE.md` 中明确写：“当 Matt 技能和 Superpowers 技能都能处理当前阶段时，优先使用 Matt 技能。” 这条规则会覆盖 `using-superpowers` 的默认优先级。方式一依赖 Agent 的理解能力，可靠性一般。

**方式二：禁用冲突技能。** Superpowers 支持“让我们跳过超能力”来停用。可以在项目配置中停用 `brainstorming`、`test-driven-development`、`systematic-debugging` 这三个与 Matt 重叠的技能，保留其余的。方式二直接、可靠，推荐。

**方式三：全量保留，但明确分工。** 不删除任何技能，但在 `CLAUDE.md` 中逐条声明：需求走 `grill-me`，不用 `brainstorming`；TDD 走 `tdd`，不用 `test-driven-development`；调试复杂问题走 `diagnosing-bugs`，简单问题走 `systematic-debugging`；执行全部走 Superpowers 的执行骨架。方式三最灵活，但要求项目配置写得足够细致。

推荐方式二或方式三。


## 六、六层工作流详解

### 第 0 层：环境配置

这是项目启动前的一次性动作。

- 安装 Matt skills 和 Superpowers skills
- 运行 `setup-matt-pocock-skills`，配置 issue tracker、triage 标签、文档目录
- 运行 `setup-pre-commit`，配置提交前 lint、类型检查、单元测试
- 运行 `git-guardrails-claude-code`，拦截危险 git 命令
- 配置 Superpowers 多代理（如果需要子代理开发）
- 只启用 Superpowers 的 `using-superpowers` 作为强制入口，但明确 Matt 技能优先用于需求、领域、架构、bug 分诊

### 第 1 层：模糊需求 → 清晰 PRD

- `grill-me`：盘问需求，走遍决策树
- `domain-model`：提取统一语言，建立领域词汇表
- `to-prd`：生成 PRD，发布到 issue tracker

这一层不要用 `edit-article`——`to-prd` 已经生成结构化 PRD，再套 `edit-article` 是画蛇添足。除非要把 PRD 改写成对外博客，否则应移除。

这一层也不要用 Superpowers 的 `brainstorming`，避免和 `grill-me` 冲突。

### 第 2 层：PRD → 可执行工单

- `to-issues`：拆成垂直切片，按依赖排序
- 每个 issue 包含验收标准、测试要求、依赖关系
- 复杂 issue 可以再用 Superpowers 的 `writing-plans` 写局部微计划，但不要每个都写

如果每个 issue 都跑完整 Superpowers 七阶段（`brainstorming` → `writing-plans` → `using-git-worktrees` → TDD → `subagent-driven-development` / `executing-plans` → `requesting-code-review` → `finishing-a-development-branch`），Token 会爆炸，进度会极慢，而且 `brainstorming` 和 `writing-plans` 在 issue 级别是重复劳动。

### 第 3 层：每个 issue 的执行循环

- `using-git-worktrees`：创建隔离工作区
- `subagent-driven-development` 或 `executing-plans`：执行任务
- `test-driven-development` 或 `tdd`：二选一，不要同时用
- `requesting-code-review`：任务间审查
- `receiving-code-review`：处理审查反馈
- `verification-before-completion`：完成前必须运行验证命令
- `finishing-a-development-branch`：合并、PR、保留或丢弃

### 第 4 层：测试检查阶段

这是原工作流缺失的部分。测试不是单一技能能覆盖的，要分层次：

- **提交前**：`setup-pre-commit` 自动跑 lint、类型、单元测试
- **任务完成**：`test-driven-development` + `verification-before-completion`
- **分支完成**：全量测试 + `requesting-code-review`
- **端到端或浏览器**：`agent-browser` 或 `webapp-testing`
- **失败诊断**：`systematic-debugging` 或 `diagnosing-bugs`，二选一
- **人工验收**：用户最终确认，无法自动化替代

测试检查应单独作为一个质量门禁层，不要混在执行里。

### 第 5 层：修改与重构

这一层要把 Bug 和架构重构分开处理，不要混用技能。

**如果是 Bug：**

- `triage-issue` → `diagnosing-bugs` → 修复 → 回到执行循环

**如果是架构重构：**

- `improve-codebase-architecture` 发现候选
- `design-an-interface` 设计目标接口
- `request-refactor-plan` 制定计划
- `to-issues` 拆成工单
- 回到执行循环

原工作流把 `triage-issue`、`diagnosing-bugs`、`design-an-interface`、`request-refactor-plan`、`improve-codebase-architecture` 混在一起用，这是错的。`triage-issue` 是 bug 分诊，不是重构；`diagnosing-bugs` 是 bug 诊断，不是重构规划；`design-an-interface` 是重构的一个子步骤。它们不在同一层，顺序也错了。

### 第 6 层：阶段完成

- `verification-before-completion`：确认所有验证命令通过
- `requesting-code-review`：最终代码审查
- 全量测试 + 人工验收
- `finishing-a-development-branch`：收尾


## 七、最终配置清单

### 安装层

- Superpowers：插件安装，全局生效，不占项目目录
- Matt Pocock Skills：项目内安装，提交 Git，按项目定制

### 项目结构

- `.claude/skills/matt/`：Matt 的 18 个技能
- `CLAUDE.md` 或 `AGENTS.md`：写清楚双框架分工规则
- `.scratch/<feature-slug>/`：Matt 的本地文件模式存放 PRD、issue、决策文档

### 触发层

- Matt 层：手动触发为主，需求、架构、重构、bug 分诊由用户主动调用
- Superpowers 层：自动触发为主，执行、TDD、审查、验证、收尾由框架自动驱动
- 冲突技能：在项目配置中明确二选一

### 分层确认

不平铺。两层通过安装方式隔离（插件 vs 项目内），通过项目配置明确优先级（需求走 Matt，执行走 Superpowers），通过禁用或声明解决重叠技能冲突。


## 八、常见错误与避坑指南

**错误一：两套框架平级同时强制。** 同时加载 Matt 和 Superpowers 两套完整技能池，Agent 不知道听谁的。Superpowers 的 `using-superpowers` 会压制 Matt 的触发，子代理又不继承启动注入的上下文，Matt 的配置在子代理里可能完全丢失。

**错误二：每个 issue 都跑 Superpowers 七阶段。** `brainstorming` 和 `writing-plans` 是全局层的动作，不应该在每个小 issue 上重复。正确做法是只在项目层做一次，或只在复杂 issue 做局部补充。

**错误三：测试检查阶段完全缺失。** 测试要分单元、集成、端到端、回归、人工验收多个层次，不是单一技能能覆盖的。

**错误四：Bug 分诊和重构规划混在一起用。** 它们是两条不同的路径，技能和顺序都不一样。

**错误五：`edit-article` 在需求阶段是错配。** `edit-article` 用于编辑对外文章，不适用于 PRD、issue、代码文档。

**错误六：`domain-model` 位置不对。** 它应该在 `grill-me` 过程中或之后、`to-prd` 之前使用，不是放在初始配置里。


## 结语

这套工作流的核心不是技能数量，而是边界清晰。Matt 层负责想清楚，Superpowers 层负责做扎实，两层通过安装方式隔离、通过配置明确优先级、通过二选一解决重叠。做到这三点，双框架就不会互相干扰，而是各司其职。
